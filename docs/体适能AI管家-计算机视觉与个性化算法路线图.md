# 体适能 AI 管家：计算机视觉与个性化算法长期路线图

## 1. 文档目的

本文档用于把《“体适能AI管家”——基于计算机视觉与个性化算法的校园健康服务平台》申报书中的长期研发方向，拆解成代码库可持续推进的工程路线。

当前项目已经具备 FastAPI 后端、React Web 前端、Android 客户端、训练记录、视频上传、姿态分析、动作评分和统计分析等基础能力。后续建设重点不是简单“接入一个 AI 模型”，而是形成一条可量化、可解释、可验证、可迭代的体适能检测闭环。

核心闭环如下：

```text
视频采集
  -> 姿态关键点识别
  -> 动作阶段识别
  -> 次数与动作质量计算
  -> 标准度评分与纠错反馈
  -> 个性化训练建议
  -> 长期健康画像与校园健康管理
```

## 2. 第一性原理拆解

### 2.1 项目真正要解决的问题

校园体适能检测的核心矛盾不是“有没有记录训练数据”，而是：

- 传统测试依赖人工观察或专用器械，成本高、流程重、主观误差大。
- 学生缺少低成本、日常化、可持续的动作质量反馈。
- 单次成绩无法解释动作问题，也难以形成长期训练建议。
- 视频动作数据、训练记录、生理指标和用户画像之间尚未形成闭环。

因此，代码库后续应围绕“让普通学生用手机完成可信的体适能检测与改进建议”推进。

### 2.2 必须保持的工程不变量

- 输入必须低门槛：普通手机摄像头或上传视频即可使用。
- 输出必须可解释：不能只给一个分数，必须说明扣分原因和改进建议。
- 评分必须可复现：同一视频在相同模型与规则下应得到稳定结果。
- 算法必须可扩展：不同动作的规则、关键点、评分权重应可插拔。
- 结果必须可追踪：原始视频、关键点摘要、评分结果、反馈和应用记录要能串起来。
- 个性化必须基于历史数据：不能凭空推荐，应来自用户长期训练表现和健康指标。

## 4. 计算机视觉建设方向

### 4.1 姿态关键点识别

目标：从视频中提取人体关键点，作为所有动作分析的底层数据。

建议推进：

- 继续保留 MoveNet 作为轻量级默认后端。
- 为 MediaPipe Pose、YOLO-Pose 等方案预留后端适配接口。
- 统一关键点输出 schema，包括关键点名称、坐标、置信度、帧时间戳、模型信息。
- 增加关键点质量过滤，避免低置信度帧污染评分。

建议模块：

```text
app/services/pose_backends/
app/services/pose_analysis_runtime.py
app/services/video_pose_analysis.py
app/services/pose_analysis_service.py
app/services/pose_features.py
```

### 4.2 视频质量检测

目标：在评分前判断视频是否可用，减少无效分析。

可检测维度：

- 人体是否完整入镜。
- 关键点平均置信度是否过低。
- 视频是否过暗或过模糊。
- 拍摄角度是否明显不适合目标动作。
- 人体是否长期遮挡。
- 有效帧比例是否足够。

输出示例：

```json
{
  "status": "invalid",
  "reason": "body_not_fully_visible",
  "feedback": ["请将手机放远一些，确保头部、肩部、髋部和脚踝完整入镜"]
}
```

### 4.3 动作阶段识别

目标：把连续视频拆成可解释的动作周期。

以俯卧撑为例：

```text
准备姿态
  -> 下放阶段
  -> 最低点
  -> 上推阶段
  -> 顶部完成
  -> 下一次动作
```

关键算法：

- 关节角度曲线。
- 肩、肘、髋关键点的相对位移。
- 峰谷检测。
- 状态机。
- 最小动作幅度阈值。
- 动作节奏稳定性检测。

### 4.4 次数统计

目标：把用户手填次数升级为 AI 自动估算次数。

优先实现：

- 俯卧撑次数统计。
- 深蹲次数统计。

建议原则：

- 只统计完整动作周期。
- 幅度不足的动作单独标记为 partial reps。
- 置信度不足的视频不强行给次数。
- 返回总次数、有效次数、无效次数和失败原因。
- 周期型动作优先复用 `app/services/exercise_rules/repetition_counter.py` 的峰谷检测，动作规则只配置关键点、角度阈值、最小时长和最小幅度。

输出示例：

```json
{
  "estimated_count": 12,
  "valid_count": 10,
  "partial_count": 2,
  "confidence": 0.86
}
```

### 4.5 标准度评分

目标：把“动作是否标准”转化为 0-100 分和可解释扣分项。

通用评分维度：

- 动作幅度。
- 身体姿态稳定性。
- 左右对称性。
- 节奏稳定性。
- 关键点置信度。
- 完整动作比例。
- 常见错误动作扣分。

评分结果应包含：

```json
{
  "score": 82,
  "grade": "good",
  "count": 12,
  "confidence": 0.84,
  "feedback": [
    "动作幅度基本达标",
    "第 4-6 次出现轻微塌腰",
    "建议降低速度并保持核心收紧"
  ]
}
```

### 4.6 错误动作识别

优先错误类型：

| 动作 | 错误类型 |
| --- | --- |
| 俯卧撑 | 塌腰、撅臀、幅度不足、手肘外展过大、身体不成直线 |
| 深蹲 | 膝盖内扣、蹲深不足、身体前倾过大、脚跟离地、左右不平衡 |
| 体前屈 | 动作幅度不足、膝盖弯曲、姿态不稳定 |
| 平衡测试 | 身体摆动过大、支撑脚移动、持续时间不足 |

建议把错误识别做成规则注册表，而不是写死在一个大函数里。

## 5. 个性化算法建设方向

### 5.1 用户体适能画像

目标：为每个用户建立长期可更新的能力画像。

建议字段：

- 基础信息：性别、年龄、身高、体重、年级、训练目标。
- 能力基线：力量、耐力、柔韧、平衡、心肺。
- 动作基线：每个动作的历史平均分、最好成绩、最近趋势。
- 训练偏好：常练动作、训练频率、训练时段。
- 风险标签：高疲劳、低恢复、动作错误高发、训练量突增。

建议新增表：

```text
user_fitness_profiles
```

### 5.2 个人基线建模

目标：评价用户是否进步，而不只是和统一标准比较。

可计算指标：

- 最近 7 天平均分。
- 最近 30 天平均分。
- 历史最好分。
- 分数趋势斜率。
- 训练频率变化。
- 动作错误复发率。
- 单次训练负荷变化。

输出示例：

```text
你的俯卧撑动作完整度近 30 天提升 12%，但最近 3 次训练节奏稳定性下降。
```

### 5.3 个性化训练建议

目标：基于用户历史表现生成下一步建议。

第一阶段建议用规则引擎，不急于引入复杂模型。

规则示例：

- 如果某动作连续 3 次低于 70 分，推荐降低强度并学习动作要点。
- 如果动作幅度不足频繁出现，推荐对应灵活性训练。
- 如果训练量一周内突然增加超过 50%，提示注意恢复。
- 如果心率偏高但完成量下降，提示可能疲劳或恢复不足。
- 如果某动作稳定提升，建议进入更高难度或增加训练量。

建议新增模块：

```text
app/services/personalization.py
```

### 5.4 弱项识别

目标：告诉用户“哪里需要补”，而不是只展示分数。

弱项维度：

- 力量：俯卧撑、深蹲完成质量。
- 柔韧：体前屈幅度。
- 平衡：单脚站立稳定性。
- 心肺：活动量、心率恢复、训练持续时间。
- 动作控制：节奏、稳定性、对称性。

输出示例：

```json
{
  "weaknesses": [
    {
      "area": "core_stability",
      "evidence": "俯卧撑塌腰错误在最近 5 次训练中出现 4 次",
      "suggestion": "增加平板支撑和慢速俯卧撑训练"
    }
  ]
}
```

### 5.5 风险提示

目标：从长期数据中识别潜在风险。

可检测场景：

- 连续训练但分数下降。
- 动作错误次数增加。
- 训练量突增。
- 心率异常偏高。
- 疲劳恢复不足。
- 重复错误动作可能带来关节压力。

注意：风险提示应避免医疗诊断化表达，只做运动健康建议。

## 6. 可穿戴设备与多模态融合

### 6.1 最小闭环建议

Android 端优先接入 Health Connect。

第一批数据：

- 步数。
- 心率。
- 活动时长。
- 消耗热量。
- 睡眠时长。

后端新增：

```text
daily_health_metrics
```

建议字段：

```text
id
user_id
metric_date
steps
active_minutes
avg_heart_rate
max_heart_rate
calories
sleep_minutes
source
created_at
updated_at
```

API 建议：

```text
POST /api/health-metrics/daily
GET  /api/health-metrics/daily
GET  /api/health-metrics/summary
```

### 6.2 融合分析方向

多模态融合不是把数据放在一起展示，而是让它们互相解释。

示例：

- 动作质量下降 + 心率升高：可能疲劳或训练强度过高。
- 步数长期偏低 + 训练频率低：建议增加低强度日常活动。
- 睡眠不足 + 训练表现下降：提示优先恢复。
- 深蹲评分提升 + 活动量稳定：说明训练适应良好。

## 7. 推荐的工程架构

### 7.1 后端模块

建议逐步形成如下结构：

```text
app/services/
  pose_features.py
  pose_analysis_service.py
  exercise_rules/
    __init__.py
    base.py
    repetition_counter.py
    pushup.py
    squat.py
    sit_and_reach.py
    balance.py
  personalization.py
  health_metrics.py
```

### 7.2 规则注册表

每个动作规则应声明：

```python
class ExerciseRule:
    exercise_key: str
    required_keypoints: list[str]
    supported_views: list[str]
    def extract_features(frames): ...
    def count_reps(features): ...
    def score(features): ...
    def feedback(score_result): ...
```

这样可以避免后续所有动作堆在 `exercise_pose_scoring.py` 里。

当前后端已经把姿态特征、峰谷次数统计、动作规则和姿态分析任务编排拆成独立模块。新增周期型动作时，优先复用 `pose_features.py` 和 `repetition_counter.py`，只在动作规则模块中声明动作别名、关键点组合和阈值。

### 7.3 数据存储建议

当前 `ExerciseRecord.keypoints_data` 能承载 MVP，但长期建议拆分更清晰：

```text
pose_analysis_results
pose_scoring_results
daily_health_metrics
user_fitness_profiles
recommendations
```

拆分收益：

- 历史分析结果可追溯。
- 评分规则版本可记录。
- 后续模型升级不会覆盖旧结果。
- 便于结题报告统计准确率和使用情况。

## 8. 分阶段路线图

### Phase 1：俯卧撑 AI 检测闭环

目标：做出最容易展示、最贴合申报书的完整闭环。

交付物：

- 俯卧撑关键点特征提取。
- 俯卧撑次数统计。
- 俯卧撑标准度评分。
- 塌腰、撅臀、幅度不足识别。
- AI 反馈写入训练记录。
- 客户端（独立仓库）展示评分与反馈。
- 至少 10 个样例视频或 mock 关键点测试。

验收标准：

- 上传俯卧撑视频后可生成次数、分数、反馈。
- 可区分标准动作和至少 2 类错误动作。
- 后端测试覆盖有效视频、无效视频、低置信度、幅度不足等路径。

### Phase 2：深蹲动作扩展

目标：验证动作规则体系能扩展到第二个典型动作。

交付物：

- 深蹲动作阶段识别。
- 深蹲次数统计。
- 蹲深不足、膝盖内扣、身体前倾识别。
- 深蹲评分和反馈。

验收标准：

- 不修改俯卧撑规则即可接入深蹲规则。
- 两个动作共用特征提取工具和评分响应格式。

### Phase 3：个性化建议 MVP

目标：从单次评分进入长期训练建议。

交付物：

- 用户最近 7 天、30 天训练趋势。
- 动作弱项识别。
- 简单建议规则引擎。
- `/api/recommendations` 接口。
- 客户端（独立仓库）建议卡片。

验收标准：

- 用户完成多次训练后能看到趋势和建议。
- 建议必须包含证据，例如“最近 5 次中 4 次出现幅度不足”。

### Phase 4：Health Connect / 可穿戴数据接入

目标：形成“动作质量 + 生理负荷 + 日常活动量”的多模态基础。

交付物：

- Android 读取 Health Connect 步数、心率、活动时长。
- 后端 health metrics 表和 API。
- 统计页展示健康指标趋势。
- 个性化建议引擎使用健康指标。

验收标准：

- Android 可同步至少 3 类健康指标。
- 后端可按日期查询和汇总。
- 建议能引用健康指标作为证据。

### Phase 5：研究评估与结题材料

目标：让项目不仅能演示，还能支撑大创结题和比赛展示。

交付物：

- 样本视频集。
- 人工标注表。
- 算法输出对比。
- 次数统计误差。
- 动作评分一致性分析。
- 用户调研问卷。
- 性能测试报告。
- 项目展示 Demo 流程。

验收标准：

- 能说明算法准确率、误差范围和适用边界。
- 能展示至少一个完整学生使用场景。

## 10. 答辩展示建议

建议答辩时不要展示“很多功能页面”，而是展示一条完整链路：

```text
学生登录
  -> 新建训练记录
  -> 手机录制或上传俯卧撑视频
  -> 后端提取姿态关键点
  -> 自动统计次数和评分
  -> 给出错误动作反馈
  -> 生成个性化训练建议
  -> 统计页展示长期变化
```

这条链路最能体现申报书中的三个关键词：

- 计算机视觉。
- 个性化算法。
- 校园健康服务平台。

## 11. 决策建议

短期不要同时铺开所有体适能项目。最优路线是先把“俯卧撑”做成标杆动作，再用“深蹲”验证架构扩展能力。

原因：

- 俯卧撑和深蹲分别代表上肢和下肢动作。
- 两者都适合手机视频采集。
- 两者都有清晰的错误动作和评分规则。
- 两者足以证明计算机视觉闭环。
- 后续扩展体前屈和平衡测试时不会推倒重来。

最终目标不是堆功能，而是形成一个可解释的算法平台：

```text
每个动作都有规则
每个评分都有证据
每条建议都有历史数据支撑
每次模型升级都有版本记录
每个研究结论都有实验材料证明
```
