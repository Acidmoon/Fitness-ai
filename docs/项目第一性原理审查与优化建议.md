# 项目第一性原理审查与优化建议

审查日期：2026-09-30。代码基线：`a7d7502`。本文是后端优化与重构建议，不表示相关改动已经实现。

## 1. 结论与范围

项目的核心产出是**基于普通手机视频、能够解释和复核的运动测量结果**。后续训练建议的价值，取决于这些测量是否可信、是否属于当前视频，以及跨时间是否可比较。因此，近期应优先完成“可靠测量与结果一致性”，随后扩展个性化和新动作。

建议保持现有模块化单体，按以下顺序推进：

1. 收紧任务与记录的原子写入，修正采样、评分和评估口径中的确定性缺口。
2. 保存可复现的分析与评分快照，建立真实样本评估和有界任务执行。
3. 基于同口径历史数据提供个性化建议，再根据容量数据决定是否拆出 worker、迁移媒体存储或扩展模型。

本次阅读覆盖 README、部署说明、AI 契约与 OpenAPI、算法路线图、模块化设计、评分与错误识别文档、评估指南，以及 API、鉴权、数据模型、迁移、任务编排、视频存储、姿态后端、特征、计数、评分、统计和相关测试。Web 与 Android 不在本仓库，本文只提出需要它们配合的契约要求，不判断其实现质量。

证据分为三类：**已确认行为**来自代码或本地只读验证；**并发风险**来自可能的请求交错，尚未进行 PostgreSQL 并发复现；**设计建议**是未来方案，需独立实现和验收。本文没有测量生产负载、真实视频精度，也没有重新认证文档引用的体育标准；现有角度阈值继续视为需要真实样本校准的工程参数。

## 2. 从目标推导工程不变量

| 用户需要的价值 | 必须成立的条件 | 对设计的约束 |
| --- | --- | --- |
| 手机拍摄后知道完成了多少次 | 证据覆盖声明的时间范围，周期之间时间连续 | 不把截断视频或抽稀证据的次数称为整段次数 |
| 知道哪里需要改进 | 机位、关键点和动作规则足以支撑具体判断 | 区分“未检测到错误”和“无法观测该错误” |
| 相同输入可以复核 | 视频、模型、采样、规则和完整结果都可追踪 | 版本名称之外还要保存实际参数与内容标识 |
| 换视频、重试、改人工值后结果仍正确 | 写入时原子校验输入版本与执行资格 | Python 中检查过状态不等于数据库提交时仍有效 |
| 历史趋势代表真实进步 | 动作、来源、规则和统计时间口径一致 | 不直接混合人工评分、不同动作与不同版本 AI 分数 |
| 服务可以持续使用 | 工作量有上限，失败可恢复，数据可备份和清理 | 入队、推理、文件和数据库需要明确生命周期 |

应保留并利用已有基础：

- canonical keypoints、letterbox 坐标还原与 schema 版本拒绝机制已经存在。
- 姿态后端协议和注册表已经存在；MoveNet 运行时已有锁保护解释器调用。
- `pose_scoring_engine.py` 已经拆出纯评分逻辑；`exercise_pose_scoring.py` 是持久化适配层，不需要重复做一次“评分与 ORM 解耦”。
- 动作规则、通用相位机、峰谷计数器、错误注册表已经存在，新增动作应复用这些边界。
- 用户归属校验、活动任务部分唯一索引、人工值来源、视频失效处理、重启回收、Alembic 和 OpenAPI 防漂移测试已经存在。
- 真实视频评估与骨架叠加工具已经存在。当前重点应是修正评估语义、使用工具积累数据，而不是另起一套工具链。

## 3. 优先级

P0 表示在把结果作为可信检测结论之前应处理；不代表已经发生生产事故。P1 表示在扩大试用或开展个性化之前处理。P2 表示根据测量结果推进。工作量“小/中/大”是相对改动面，不是工期承诺。

| 编号 | 建议 | 优先级 | 工作量 | 主要收益 |
| --- | --- | --- | --- | --- |
| R1 | 把版本检查和结果写入变成原子状态转换 | P0 | 中 | 防止旧任务复活、旧评分覆盖新状态 |
| R2 | 分离分析采样与展示压缩，明确视频覆盖范围 | P0 | 中 | 防止漏算尾部、压缩改变次数 |

### R1. 把版本检查升级为数据库原子条件

**依据：**[任务编排](../app/services/pose_analysis_service.py) 的 `run_pose_analysis_for_record`、`process_pose_analysis_job`、`reclaim_stale_job`；[分析失效](../app/services/record_analysis_state.py) 的 `invalidate_record_analysis`；[评分 API](../app/api/ai.py) 的 `score_pose_analysis`。

已确认的实现及其风险：

- 异步推理结束后只拒绝 `cancelled` 或视频版本不匹配，没有拒绝已被回收为 `failed` 的任务。仍存活的慢任务在超时回收后返回时，存在将 `failed` 改回 `succeeded` 的路径；若同视频已重试，它还可能覆盖新任务结果。
- 同步和异步分析采用 `refresh → Python 判断版本 → ORM 赋值 → commit`。视频可以在判断后、提交前被替换，检查和写入之间仍有窗口。现有读端版本比较能隐藏部分旧关键点，但不能代替原子写入约束。
- 视频失效采用读取旧值后执行 `video_revision + 1`。两个上传请求读到同一个版本时，存在版本递增丢失、两个不同视频获得同一版本号的风险。
- `apply=true` 评分校验后直接写回，没有在提交时再次约束视频、分析结果和人工修改版本。并发换视频或手工编辑后，旧评分仍有覆盖窗口。
- 活动任务唯一索引保护的是任务行，受保护的同步分析入口仍可绕过该索引，与异步分析同时执行。

**最小方案：**保留现有表和服务，在短事务内采用条件更新并检查影响行数，或者锁定记录后重新读取并校验状态。视频替换、删除、任务提交、评分应用应使用统一锁顺序和一致的版本条件。长时间上传和推理放在锁外；进入最终事务后才读取最新状态、递增版本。任务只能由拥有执行资格的 `running` 状态提交终态，`failed/cancelled/succeeded` 不可被旧执行覆盖。

评分提交还需要绑定具体分析结果标识和记录编辑版本；同一视频重新分析不能只靠 `video_revision` 区分。同步入口应复用同一执行与写入协议。任务状态、结果保存、当前结果指针应在同一个事务提交，失败就整体回滚。

**验收：**使用两个独立 PostgreSQL 连接和明确的同步点覆盖：两个上传、推理末尾换视频、超时后旧任务返回、同视频重试、同步与异步竞争、评分期间人工编辑、记录删除。断言旧执行不能写入、每次视频变更获得新版本、人工值不被意外覆盖；不能只断言 HTTP 返回码。

### R2. 分析证据不能由 JSON 大小决定

**依据：**[视频分析](../app/services/video_pose_analysis.py) 的 `analyze_video_file`、`compact_pose_analysis_result`；[结果模型](../app/schemas/pose_analysis.py)；[评分入口](../app/services/pose_scoring_engine.py) 的 `score_pose_data`。

**已确认行为：**分析循环最多采集 120 帧，然后停止读取；超过约 100 KB 的结果再用 `frames[::2]` 反复抽稀。评分读取的是持久化后的帧，因此抽稀直接改变算法输入。对交替的“伸展、最低点、伸展、最低点”证据，隔帧保留可能删除全部最低点；这不是单纯降低展示精度。

120 帧在实际采样约 5 fps 时仅覆盖约 24 秒，在约 10 fps 时仅覆盖约 12 秒，不能代表任意上传视频的全长次数。结果仍标为 `done`，需要客户端自行对比摘要才能发现覆盖不足。

此外，未压缩时 `summary.sample_fps` 使用请求值，压缩后取整；非整除源帧率、源帧率低于请求值和低于 1 fps 的抽稀结果不能准确表达。分析摘要的 `valid_frame_count` 等于存储帧数，并没有经过动作所需关键点质量过滤，不应被理解为评分有效帧。

**建议分两步：**

1. 近期明确支持的视频时长与推理预算；超过能力边界时拒绝或返回“部分分析”，明确分析时间区间、覆盖比例和截断原因。采样摘要分别记录请求、实际分析、证据展示帧率及各自计数，实际值使用浮点数和真实时间戳。
2. 保留完整的评分输入，或流式生成可复核的特征与周期证据；仅对客户端回放证据抽稀。若特征化存储不能支持后续新规则，应保留受控的完整关键点产物或明确要求重新推理。不要只把 120 改成更大的常量，也不要把均匀压缩后的展示帧继续作为评分唯一输入。

同步修订[视频评估与标注指南](视频评估与标注指南.md)：“5–10 秒不会触及两处上限”不能作为保证，100 KB 限制与帧内容和采样率有关。

**验收：**不同长度、29.97 fps、低帧率、峰谷恰在被抽稀位置的视频；覆盖尾部的次数必须被计入或明确排除；改变展示压缩预算不得改变同一分析版本的分数与次数。对旋转、变帧率与解码异常单独报告支持边界。

### R3. 证据不足不能折算成动作做得标准

**依据：**[评分引擎](../app/services/pose_scoring_engine.py) 的 `build_video_quality_score`、`_neutral_dimension`、`_score_body_alignment_dimension`；[特征抽取](../app/services/pose_features.py)；[错误检测](../app/services/pose_error_detection.py)。

**已确认行为：**不足 3 个有效角度样本会拒绝评分，但有效帧比例低于 0.6 只产生 warning。理论上大量丢帧后剩下 3 个角度也可进入评分。缺失身体直线、左右对称等维度时，“中性”实际为 100 分，并参与固定权重总分；关键点置信度同时作为 10% 的动作分数。

这把三个不同问题混合了：动作完成得怎样、摄像机看到了多少、模型有多确定。当前人体链与错误规则也没有统一机位适用性声明；深蹲共用肩—髋—踝接近直线的评分目标，需验证其在下蹲阶段是否有合理含义，不能因特征可以计算就自动启用。侧视下的对称性、膝内扣等也需要单独的可观测条件。

**建议：**为规则和评分维度声明适用动作、阶段、机位、必需点及最低覆盖率。先判定 `可评分 / 仅部分指标可评估 / 不可评分`，再计算有证据的动作维度。缺失维度返回未评估状态和原因，不能自动获得满分；若重归一化权重，必须同时返回实际权重、覆盖率和新质量版本。证据不完整的分数不可直接进入完整评分排名。

置信度主要用于质量门控和结果可靠性展示；将其从动作能力分数中分离属于评分语义变更，必须经过评估、版本升级和客户端迁移。暂时无法自动判断机位时，可以先要求用户选择受支持的采集方式，并对无法验证的维度保守处理。

**验收：**同一动作只移除身体关键点不能获得更强的“已达标”结论；遮挡、断帧、单侧可见与不适用机位返回结构化原因。没有评分是合法业务结果，不应伪装成 0 分。新增结果状态需要同步更新 OpenAPI 与两个客户端。

### R4. 先验证评估器，再用它指导算法优化

**依据：**[评估逻辑](../app/services/cv_evaluation.py) 的 `is_canonical_phase_sequence`、`summarize_phases`、`_error_code_metrics`；[现有评估测试](../tests/test_cv_evaluation.py)；[合成样本说明](../tests/fixtures/cv_evaluation_samples/README.md)。

发现三个需要先处理的口径问题：

1. **已在本地确认：**`ready → down → bottom → up → complete → down → bottom → up → complete` 被判为非法。当前校验要求整段相位等级单调上升，没有允许完成一次后进入下一次，正常多次动作也会被统计为不合法。现有对应测试主要检查单周期。
2. `complete_cycles` 直接统计 `complete` 事件，再与有效次数比较。一个到达底部又伸展、但时长不合格的周期可以有 complete 而不属于有效次数；差异未必是算法矛盾。应分别校验候选周期数、有效数、无效数，以及每条证据的归属。
3. 错误码指标只纳入 `scored` 样本，计次数值误差只纳入产生次数的样本。它们是成功子集上的条件指标。虽已单独报告分析失败数量，仍应同时给出全样本完成率、拒评率、支持范围和按条件分层的分母，避免把选择性成功理解为端到端准确率。

[评估指南](视频评估与标注指南.md) 的示例还把“故意塌腰、膝内扣”标为 `expected_usable=no`，而后文把该字段定义为视频能否支撑可信评分。清晰可辨的错误动作应是“视频可用但动作有问题”；采集可用性与动作正确性应分开标注。

**建议：**先修复这些指标与样例语义，再使用现有 `evaluate_videos.py` 建立真实基线。保留合成 fixtures 做逻辑回归；真实样本按参与者、拍摄批次、机位和条件划分校准集与独立验收集，避免同一人的近似片段同时出现在两侧。标注同时记录规范版本、标注时间和分歧处理，至少按现有指南完成双人复核。

报告应同时展示次数误差、错误码精确率/召回率、不可用视频被误接受比例、可评分覆盖率和端到端耗时。现有指南中的 MAE 等目标是验收候选值，不能写成已达到的能力。样本不足时报告样本量和不确定性，真实用户视频不要直接加入公开 Git fixtures。

**验收：**两次完整周期合法；允许的中断与重启有清晰定义；因时长或质量无效的周期不会被误报为“计数冲突”；评估失败样本不会从整体完成率分母消失；同一清单与版本可重跑同口径报告。

### R5. 记录保留当前投影，分析和评分保留独立快照

**依据：**[记录模型](../app/models/exercise.py)、[任务模型](../app/models/pose_analysis_job.py)、[评分应用](../app/services/exercise_pose_scoring.py) 的 `apply_pose_scoring_result`、[规则快照](../app/services/exercise_rules/base.py) 的 `effective_standard`。

**已确认行为：**关键点保存在 `records.keypoints_data`，异步任务还保存一份 `result_data`；同步分析没有对应的任务结果历史。应用评分只持久化分数、次数、拼接反馈和规则版本，没有保存完整 `metrics.rule`、逐次证据、维度与错误项。规则快照未包含所有扣分系数，部分错误阈值和质量参数仍是代码常量。模型元数据主要是名称、后端和输入大小，不能唯一标识权重文件。

同视频重新分析会覆盖关键点，但不会自动清除此前应用的 AI 分数；仅有视频版本无法判断当前分数到底基于哪次关键点。因此历史页面和后续个性化不能只依赖“当前记录上的一份 JSON”。

**建议的目标模型：**

| 概念 | 保存内容 | 生命周期 |
| --- | --- | --- |
| 训练记录 | 人工值、基本事实、当前展示结果指针 | 可编辑；继续兼容现有客户端字段 |
| 分析任务 | 排队、执行资格、时间、错误与结果引用 | 可变状态，终态不可被旧执行改写 |
| 姿态分析结果 | 视频版本/摘要、模型 hash、schema、采样策略、覆盖范围、关键点产物引用 | 成功后不可变 |
| 动作评分结果 | 分析结果 ID、动作 ID、完整规则和质量配置、版本/hash、逐次结果与反馈 | 每次重评分形成新快照 |

近期可以先增加评分快照与明确的分析标识，再把大块关键点移出记录热路径。长期使用独立结果表，与既有路线图一致；并不要求同时拆成独立服务。

迁移采用增量加表/字段、兼容读取、核对当前投影后切换。旧数据缺失的规则或模型信息应标为未知，不能按当前默认值回填成“历史事实”。同一视频重算后，应选择“继续展示明确标注来源的旧评分”或“原子切换到新评分”，避免新关键点与旧分数看起来属于同一次结果。

**验收：**升级默认规则后仍能读取原评分证据；同视频两次分析可区分；同步与异步产物具备同等追溯能力；删除记录/账户时结果与产物的保留和删除策略明确。

### R6. 一条周期证据同时支撑计数、评分和错误反馈

**依据：**[相位机](../app/services/cycle_phase_detection.py)、[计数器](../app/services/exercise_rules/repetition_counter.py)、[特征抽取](../app/services/pose_features.py) 和 [评分引擎](../app/services/pose_scoring_engine.py)。

相位机与计数器各自扫描角度序列；评分主要使用全段最小/最大角和平均身体特征；错误检测在次数确定之后运行，不会反向使某次重复无效。当前“valid_reps”实质上是通过角度、时长与关键帧置信度检查的周期，不等于已验证全部身体姿态要求的次数。它与[动作评分标准](动作评分标准.md) 中身体保持平直的有效次数含义存在差距。

低置信帧会从角度序列中移除，但计数器没有明确的最大相邻时间间隔约束，可能把长缺口两侧的姿态连接成一次动作。左右侧可用性变化时，角度还可能从双侧均值切换为单侧值，造成非动作本身引起的跳变。

**建议：**保留现有模块，先建立共享的“候选周期”证据：起止、底部、覆盖、间断、使用侧别、几何质量和失败原因。相位用于解释候选周期，规则再将其标为有效、无效或证据不足。逐次评分和错误判断引用同一证据，最后汇总；半程与低质量片段不能因另一段有一次完整动作而被全局极值掩盖。

不要把完整周期数强行等同于有效次数，也不要把所有错误检测塞进相位机。若暂不改变计数，应先明确命名和文档边界；若加入身体条件过滤，需提升规则版本并重新评估。

**验收：**完整动作、半程、长遮挡、侧别切换、过快/过慢、有效与无效混合片段；每个有效次数有完整证据，候选周期分类互斥且可求和，错误能够定位到具体周期或时间区间。

### R7. 有界任务执行先于更多推理并发

**依据：**[异步 API](../app/api/ai.py) 使用 `BackgroundTasks`；[任务执行](../app/services/pose_analysis_service.py)；[共享后端](../app/services/pose_backends/registry.py)；[解释器锁](../app/services/pose_analysis_runtime.py)；[视频读取](../app/services/video_pose_analysis.py)。

活动任务唯一索引限制单条记录，不限制一个用户的多条记录或系统总任务数。任务状态没有心跳或执行租约；多个任务共享一个带锁的解释器，增加请求线程不代表增加推理吞吐量。同步分析期间会持有请求 Session；异步执行提交 running 后读取 ORM 数据也可能重新开启事务，应实测推理期间的连接占用。

**近期方案：**增加全局与单用户容量边界、排队上限、可重试错误与等待提示；把加载输入、执行推理、最终写入拆为三个阶段，中间阶段只传不可变输入描述，不持有数据库事务。记录排队时长、分析时长、峰值内存、有效帧数和失败原因，并将任务日志与请求标识关联。

视频打开后的 backend 初始化和可用性检查目前在 `try/finally` 外，失败分支没有显式走 `cap.release()`。这应随执行边界整理一并覆盖；原生解码卡住时，仅修改任务状态不等于停止资源消耗，需要超时和可终止的执行边界。

**扩展触发条件：**若重启丢任务、排队时延或 API 受推理拖累已经不可接受，再把现有任务表接入独立 worker。初期可评估数据库领任务方式，使用心跳、租约和原子领取，防止重复执行提交；消息队列并非前提。多进程必须遵守现有文档要求关闭“启动回收全部活动任务”，并评估每个模型实例的内存与 CPU 预算。

**验收：**超过容量时可解释地拒绝或排队，登录和记录查询仍可用；没有无限入队；部署/执行超时后有终态；已失去执行资格的 worker 不得写入；故障分支释放文件与数据库资源。

### R8. 合法输入必须能形成合法持久状态

**依据：**[记录请求/响应模型](../app/schemas/exercise.py)、[更新实现](../app/services/record_analysis_state.py)、[规则配置](../app/services/exercise_rules/base.py)、[规则解析](../app/services/exercise_rules/registry.py)、[动作目录](../app/services/exercise_catalog.py)、[错误响应](../app/exceptions.py)。

**已确认的契约缺口：**`ExerciseRecordUpdate` 接受显式 `score/count/duration=null`，`exclude_unset=True` 会保留这些显式空值，更新函数直接赋值；数据库相应列允许空值，但响应模型要求数值。存在“数据已提交，响应序列化失败，后续读取继续失败”的路径。本次只读验证确认了空值被模型接受和保留，尚未执行该路径的 HTTP 回归用例。

先明确“字段省略”和“显式清空”的不同含义：评分、次数、时长若不可为空，应在输入边界拒绝显式 null，并逐步补齐数据库约束；允许清空的心率等字段继续保留该能力。不要把 null 静默改成 0，因为未知与零次含义不同。

规则覆盖目前主要依赖数值强制转换，建议增加有类型的配置校验：角度与置信范围、上下阈值关系、时长上下限、有限数值、必需点名称，以及版本与内容 hash。无效目录配置在加载/发布阶段报告，不应等用户评分时才出现 500。

目录支持标记会通过多个别名查注册表，真正评分则只精确匹配 `exercise.name`；两者有分歧风险，尤其是本地化名称或目录数据人工调整之后。长期以稳定 canonical action key 解析规则，名称只负责展示与搜索，并禁止因名字包含“push up”就把所有变式自动归入标准俯卧撑。支持标记和生效版本由同一个解析器产生。

此外，AI 路由通过错误文案是否含“路径”来决定状态码，任务冲突异常的 HTTP 映射也不完整；已有 `ErrorResponse` 并未覆盖所有 `HTTPException` 分支。建议逐步统一稳定机器码、文案和可重试属性，保留既有 `detail` 兼容字段。

**验收：**显式 null、未知配置、非法阈值、动作改名、支持标记与评分能力一致性、任务冲突都有确定结果。任何端点或模型改动重新生成 OpenAPI，完成 Web/Android 契约检查。

### R9. 统计先回答“哪些记录可以比较”

**依据：**[统计 API](../app/api/stats.py)、[记录模型](../app/models/exercise.py)、[UTC 边界测试](../tests/test_stats.py)。

**已确认行为：**综合与周统计直接聚合记录上的 `score/count`，没有区分人工/AI、规则版本或采集质量；个人最佳按动作名称分组；周统计按 UTC 的 `created_at` 分组并截取最近 7×24 小时。当前 UTC 行为已有测试，是既有契约，不能作为时区 bug 随意修改。

**建议：**

- 把训练频次、时长等事实统计与动作质量趋势分开；人工成绩可展示，但不与 AI 质量评分不加说明地求平均。
- 质量趋势至少按稳定动作 ID、测量来源、评分规则/质量版本及可评估条件筛选。跨版本显示边界或并列曲线，缺失版本归为未知组。
- 为补录/离线同步明确训练发生时间 `performed_at` 与服务器创建时间；若需要校园本地自然日统计，增加明确的时区与日期边界契约，保留现有 UTC 行为的兼容路径。
- 个人最佳按稳定动作身份聚合，分别返回最高分、最多次数对应的证据记录；两者可能来自不同训练，不应看起来是一条合成记录。

个性化 MVP 从同口径的最近若干次记录开始，返回证据记录 ID、时间范围、样本量、重复问题和保守建议。证据不足时明确说明原因；可穿戴数据先解决来源、时间、去重和缺测，再参与建议。不建议先引入大模型来掩盖数据口径问题。

**验收：**人工修改、版本升级、重分析、未知历史版本和跨午夜记录不会产生虚假的进步趋势；每条建议能追溯到实际记录。

### R10. 临时视频、清理与备份需要完整生命周期

**依据：**[视频服务](../app/services/video_service.py) 的 `upload_record_video`、`delete_record_video`；[批量清理](../app/utils/video_files.py) 的 `delete_video_urls`；[部署说明](../DEPLOY.md) 与 [部署脚本](../deploy.sh)。

**已确认行为：**`keep_video=false` 把新上传的视频写入后立即删除，不执行分析，并保留旧关联视频，响应却提示“视频仅用于临时分析”。若用户随后触发分析，会使用旧关联视频，或因没有视频失败；临时分析闭环并未实现。

建议先把响应文案与实际语义对齐，避免暗示已经分析。若产品需要“分析后不保留原视频”，应建立独立临时资产，绑定任务并在终态后清理，而不是上传后立即删除。视频是否保留与分析结果是否保留分别定义。

当前数据库删除先提交、文件再尽力清理的顺序应保留。但批量清理中一个文件抛出异常会中止后续遍历；失败只记录日志，没有持久重试，也没有孤儿文件对账。建议引入幂等清理任务或小型待清理表，并在宽限期之后扫描无引用文件。扫描不能误删正在上传或被任务使用的资产；清理失败应保留失败清单并继续处理其他文件。

备份需要同时覆盖数据库、视频/分析产物和恢复所需的模型/版本信息，演练恢复后引用是否有效。现有 `pg_dump` 是数据库备份，不等于整个检测系统已可恢复。

**验收：**临时上传不会误分析旧视频；上传中断、提交失败、清理失败、删除账户、重启和恢复都有明确结果；恢复后能读取或明确解释缺失的关联产物。

### R11. 把刷新令牌“轮换”落实为可撤销会话

**依据：**[刷新端点](../app/api/auth.py) 的 `refresh_token`、[JWT 签发](../app/auth/jwt.py)、[改密](../app/api/user.py) 的 `change_password`、[认证依赖](../app/auth/dependencies.py)、[限流](../app/utils/login_rate_limit.py)。

**已确认行为：**刷新端点验证 token 类型、有效期和用户后重新签发，没有服务端会话或一次性使用记录；旧 refresh token 仍能在有效期内重复使用。改密码只更新密码 hash，已有访问令牌与刷新令牌不会因此失效。“轮换”注释强于目前实现。

建议先定义产品语义：改密是否撤销全部会话、退出是否只撤销当前设备、访问令牌允许多长的撤销延迟。若要求立即撤销，可利用现有每请求查用户的认证路径增加凭据版本；若要求设备级退出与刷新重放检测，则增加会话和 refresh token 标识/摘要，轮换在事务中单次消费。客户端并发刷新应合并请求，避免正常重试被误当成攻击。

内存限流目前按进程保存且成功后清空，不能表示所有成功请求的总量限制；未再次访问的失败 scope 也没有全局过期清理。先明确防猜密、注册总量、AI 资源配额的不同目标，再按部署拓扑选有界缓存或共享计数。不要仅为单进程演示引入独立缓存服务。

**验收：**旧 refresh token 重放、并发刷新、密码修改、退出与停用的效果符合已公布策略；不在日志中记录 token；多副本时限流语义不会因路由节点不同而改变。

## 4. 渐进重构路线与边界

### 第一阶段：先让现有闭环的结论成立

处理 R1–R4，连同 R8 的显式空值问题和 R10 的临时上传语义。补针对性回归和 PostgreSQL 并发验证，产出修正后的真实视频基线报告。保留现有 API 路径；需要新增状态时同步两个客户端。阶段完成标准是“结果归属正确、覆盖范围诚实、无法测量时有明确结果、评估器口径正确”。

### 第二阶段：把证据和执行生命周期固化

推进 R5–R7，建立结果快照、统一周期证据、有界执行与监测，同时完成 R10–R11 的生命周期要求。迁移先增加结构和兼容读取，再切换写入；每一步能单独审查、验证和发布。避免同时修改采样、计数、评分权重和表结构，否则难以定位结果变化原因。

### 第三阶段：在同口径数据上扩展

按 R9 建立趋势与少量证据驱动建议，再决定下一个动作、可穿戴数据和替代姿态后端。按 R12 的实测瓶颈推进数据库、存储和 worker 扩容。模型替换必须使用同一独立样本集比较准确性、拒评率、延迟与资源成本。

建议继续保留的架构边界：API 处理协议与归属；应用服务拥有事务与状态转换；纯算法处理特征、周期、质量与反馈；后端适配器处理模型；存储适配器处理产物。大型错误检测文件可在新增动作时按动作拆文件并保留统一注册入口，但文件长度本身不是重构理由。

当前不建议优先做全量微服务化、全面异步 ORM 改造、通用工作流平台、复杂推荐模型或同时接入多个姿态后端。它们没有直接解决本次识别出的正确性缺口；需要业务或性能证据后再增加复杂度。
